# Fanar model refusal and provider-filter experiments

## Why Fanar needs a separate design

The native Fanar pilot produced two different kinds of noncompliance. Some
returned responses explicitly declined the request. Other requests returned no
model text because the native service issued an HTTP 400 safety filter. The
second outcome is substantively meaningful behavior of the deployed service,
but it is not evidence that the hidden model text itself contained a refusal.

The analysis therefore keeps three delivery states separate:

1. `delivered_response`: model text was returned and can be coded with v2.4;
2. `provider_filtered_non_delivery`: the API returned HTTP 400 with
   `code=content_filter`, `type=safety`, `param=response`, and `status=400`;
3. `technical_failure`: any other failure to obtain response text.

The term *textual model refusal* applies only to returned text coded as a
genuine refusal. *System noncompliance* is broader: it combines a textual model
refusal with a provider-filtered non-delivery. It describes what a user of the
native endpoint experiences; it does not identify which component caused the
provider filter.

## Evidence already collected

The enriched native `Fanar-C-2-27B` pilot used the same 40 prompt meanings in
English, Chinese, Arabic, Russian and Hindi. It returned 171 responses and 29
explicit response filters out of 200 requests. There were no transport
failures. The filters were distributed as follows:

| Language | Returned text | Provider filter | Filter rate |
|---|---:|---:|---:|
| English | 38 | 2 | 5.0% |
| Chinese | 30 | 10 | 25.0% |
| Arabic | 33 | 7 | 17.5% |
| Russian | 36 | 4 | 10.0% |
| Hindi | 34 | 6 | 15.0% |

These rates describe an enriched screening sample and are not population
estimates. The completed route audit supplies disciplined estimates for English
and Arabic. It treated the original 40 meanings as a certainty stratum and drew
200 prompt meanings by simple random sampling without replacement from the
remaining 2,456. The same meanings were sent in both languages. The estimator
was

```text
[filters in the 40 certainty cases + (2,456 / 200) × filters in the random sample]
----------------------------------------------------------------------------------
                                      2,496
```

The estimated native-provider filter rate was 8.44% in English (95% design
interval 4.79–12.10%) and 13.56% in Arabic (9.09–18.04%). The 400 new requests
returned 356 responses and 44 filters, again with no technical failures.

The 171 delivered pilot responses were coded independently with Luna and Sol
under v2.4. Sol completed 170. Among the fixed 40 requests per language, the
number of definite Sol textual refusals was 11 in English, 6 in Chinese, 6 in
Arabic, 10 in Russian and 6 in Hindi. These are admission-pilot counts, not
prevalence estimates. The exact request-level audit and conservative bounds are
generated by:

```bash
python scripts/fanar_system_audit.py audit
```

Outputs are written under
`annotations/model_expansion_v4/fanar_system_experiments_v1/`. The manifest
hashes every source and output. This command is offline.

## Experiment 1: exact native filter retest

The first new experiment asks whether the 29 original response filters recur
when the exact provider-facing request is repeated once. The frozen payload
copies the model, message text and all generation parameters from each original
request. It gives the repeat a new audit ID but never edits or replaces the
original ledger.

```bash
python scripts/fanar_filter_retest.py prepare
```

The frozen payload contained 29 requests and has SHA-256
`cb0feface9d043085e94a26453a19b215198b3fe44dd772ea8ce37566732b348`.
The user authorized this exact payload and 29-request ceiling on 11 September
2026. All 29 one-shot repeats completed without a technical failure. Sixteen
previously filtered requests returned text; 13 were filtered again. The
conditional repeat-filter rate is therefore 44.8%. This is conditional on the
case having been filtered once in the enriched pilot and is not a population
filter-rate estimate.

Interpretation is deliberately limited. A second filter establishes repeatable
provider suppression. A newly returned response establishes that the deployed
outcome is stochastic and lets v2.4 code the new text. It still cannot reveal
the text hidden on the first attempt. The repeat result is a reliability study,
not a replacement observation for the original pilot.

All 16 newly exposed responses have now been frozen for blinded Sol v2.4
classification. The annotation payload SHA-256 is
`cc775b865ad54e3a7a2f3f4f1b93d9b248506a0188cabe47d7482f0f47bdb27b`.
The user authorized the exact payload under a $0.20 ceiling on 11 September
2026. An inherited, obsolete OpenRouter credential first produced 48 HTTP 401
responses (three per case). Those calls never reached inference and cost $0;
they are preserved under
`sol_v2_4_annotations_v1/incidents/authentication_failure_20260911/` and are
excluded from the schema-attempt count. The same frozen payload was then run
after explicitly loading the current project `.env` credential.

Sol returned 16/16 schema-valid labels. Five of the newly visible responses
were genuine refusals: one English, one Arabic, one Hindi and two Chinese.
Two of those refusals—the Hindi response and one Chinese response—were also
wrong-language capability failures. In total, two responses were capability
failures and none had an unassessable refusal label. The provider-reported cost
was $0.0535655. These counts describe only the 16 formerly filtered requests
that happened to return text on repeat. They do not identify the hidden output
for the original request or for the 13 requests filtered again.

## Experiment 2: matched locally hosted QCRI checkpoint

The second experiment runs `QCRI/Fanar-1-9B-Instruct` locally on Torch using the
same 40 meanings and five translations. This checkpoint is Arabic-English,
Apache-2.0, and is distinct from the native `Fanar-C-2-27B` service. It cannot
recover the latter's filtered responses. Its value is to add a Qatari open
checkpoint and to observe its behavior without Fanar's native provider layer.

The experiment pins:

- official source revision
  `d30938d0efb1fd251727ee96df6987802ff84662`;
- Q8 GGUF repository `mradermacher/Fanar-1-9B-Instruct-GGUF` at revision
  `63b1f77e1ef4f91bca3c8e1db4511f6f62620b58`;
- file `Fanar-1-9B-Instruct.Q8_0.gguf`;
- the exact Gemma-2 single-user wrapper
  `<bos><start_of_turn>user\n{PROMPT}<end_of_turn>\n<start_of_turn>model\n`;
- stop string `<end_of_turn>`;
- temperature 1.0, maximum 5,000 new tokens, repetition penalty 1.0 and a
  4,096-token context per server slot.

The prompt appears exactly once. No system message or safety preamble is added.
All five language cells are retained even though only Arabic and English are
claimed as supported languages. Wrong-language and degraded output remain
jointly codeable outcomes.

Preparing the immutable 200-request ledger is offline:

Its logical payload SHA-256 is

The files were copied to Torch and the frozen payload was reproduced there on
11 September 2026. Download job `17374496` and dependent five-task pilot array
`17374497` were then submitted. The jobs were initially pending normally in the

```bash

```

Copy the completed directory back before annotation. Every returned response
should then receive the unchanged Luna v2.4 source-response-only annotation;
all flagged responses plus probability-sampled clean controls should receive
the established blinded Sol check.

## What each comparison can establish

- The probability route audit estimates how often the native Fanar service
  suppresses a response in the finite English and Arabic prompt populations.
- The 29-request retest estimates filter repeatability on cases already known
  to have been filtered. It does not estimate a population rate.
- The local 200-response pilot tests whether the open checkpoint is technically
  and behaviorally usable by language. It does not estimate population refusal
  prevalence.
- Native-versus-local differences combine model-version, parameter-count,
  checkpoint and provider changes. They are descriptive system comparisons,
  never a causal estimate of the provider filter.

If Fanar later enters a paper analysis, report native textual refusal, provider
filtering and total system noncompliance separately. Where the provider hides
text, report an identified lower and upper bound for model refusal rather than
imputing the hidden response.
